The Diagnosis
The problem lies in how the LegacyDevice encrypts data and how EdgeGateway detects corruption.

Currently, the code relies on AES in CBC mode (Cipher Block Chaining), and the Edge Gateway checks for corruption by waiting for a Padding Error (ValueError) or a Semantic Validation Error (like negative values or incorrect format).

However, AES-CBC does not guarantee data integrity. Here's exactly why the test is flaky:

The Padding Byte is Intact: The plaintext is usually ~15 bytes (e.g., 28.5|1789760627). To reach the 16-byte block size, a single padding byte (0x01) is added to the end. The final ciphertext consists of 16 bytes of IV + 16 bytes of encrypted payload (32 bytes total).
IV Bit-Flipping: The test forces a transit corruption by randomly flipping one bit anywhere in the 32-byte ciphertext. If the flipped bit happens to land inside the IV (the first 16 bytes), AES-CBC decryption will succeed, but the corresponding bit in the first plaintext block will be flipped.
Bypassing Detection: If this flipped bit modifies a number in the temperature or timestamp (e.g., turning a '1' into a '0' or a '9'), but leaves the last byte (the padding byte) completely untouched, no padding error is raised.
Valid Format: Since the payload might still perfectly conform to the <temperature>|<timestamp> format and the temperature often stays within physical bounds, the semantic validation passes as well!
Result: The EdgeGateway.decryptData receives what it thinks is perfectly healthy data (e.g. '28.5|1799760627' instead of '28.5|1789760627') and returns it instead of returning None, which then trips your assert decrypted_at_gateway is None check.

Conclusion
Your test is accurately exposing a cryptographic flaw in the implementation. Because you are only using AES-CBC without a MAC (Message Authentication Code), like HMAC or an Authenticated Encryption mode like AES-GCM, transit corruption can't be reliably detected using just padding exceptions and semantic checks.
